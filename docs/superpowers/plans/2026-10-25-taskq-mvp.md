# taskq MVP — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** очередь фоновых задач на Go и Postgres: HTTP API, пул воркеров с повторами, арендой и graceful shutdown, метрики, chaos-демо.

**Architecture:** один бинарник `taskq` с подкомандами `api`, `worker`, `migrate`. Процессы `api` и `worker` общаются только через таблицу `jobs`. Воркер забирает задачи через `UPDATE … FOR UPDATE SKIP LOCKED`. Интерфейсы объявляет потребитель (`api`, `worker`, `metrics`), а `store` экспортирует конкретный `*store.Postgres`.

**Tech Stack:** Go 1.27, `net/http`, `log/slog`, `pgx/v5`, `goose/v3`, `prometheus/client_golang`, `testcontainers-go`, `testing/synctest`, golangci-lint v2, Docker Compose, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-25-taskq-design.md`

**Кто исполняет:**
- **[Claude]** — задачу целиком (тесты и код) делает Claude, по циклу TDD «один тест за раз».
- **[автор]** — **тесты пишет Claude, продакшн-код пишет автор.** Тесты, перечисленные в Step 1 задачи, Claude пишет, когда автор берёт задачу в работу. Все остальные шаги выполняет автор. Порядок описан в разделе «Процесс работы над задачей [автор]».
- В конце каждой недели Claude задаёт 5 вопросов с собеседования по её теме.

## Global Constraints

- Модуль `github.com/alians84/taskq`, `go 1.27`.
- Внешние зависимости только: `github.com/jackc/pgx/v5`, `github.com/pressly/goose/v3`, `github.com/prometheus/client_golang`, `github.com/testcontainers/testcontainers-go` (+ `modules/postgres`). Если нужна новая зависимость, её сначала обсуждаем.
- Линтер: golangci-lint v2, версия закреплена в `tools/go.mod`, запуск через `make lint` (`go tool -modfile=tools/go.mod golangci-lint run ./...`).
- Definition of Done для задачи и PR: `make lint` чистый, `make test` (`-race`) и `make test-integration` зелёные, тесты из Step 1 задачи не изменены автором.
- Время вычисляется только через `now()` в БД, Go передаёт только `time.Duration`.
- Ошибки оборачиваем как `fmt.Errorf("<pkg>: <op>: %w", err)`. Ошибки pgx не выходят за пределы `store`.
- Моки только в виде написанных руками fake-реализаций, без mockgen.
- Статусы задач строго `pending | running | succeeded | dead`.
- Значения по умолчанию и лимиты:
  - `max_attempts` = 5 (допустимо 1–25);
  - payload ≤ 65536 байт;
  - `limit` = 50 (допустимо 1–200);
  - backoff: base 1s, потолок 10m, equal jitter;
  - `JOB_TIMEOUT` 30s, `LEASE_MARGIN` 10s, `SHUTDOWN_TIMEOUT` 25s;
  - `POLL_INTERVAL` 1s ± 20%;
  - `WORKER_CONCURRENCY` 10;
  - таймаут итоговой записи 5s, таймаут Claim 5s, таймаут сбора `queue_depth` 2s;
  - Postgres `postgres:18-alpine`.
- Ветки `wN/<тема>`, PR в `main`.

## Процесс работы над задачей [автор]

1. **Карточки.** В начале недели Claude кладёт карточки задач в `tasks/week-N.md`. Это локальный файл, он исключён из git через `.git/info/exclude` и в репозиторий не попадает. В карточке:
   - цель задачи;
   - сигнатуры из блока Interfaces;
   - какие понятия Go в ней тренируются;
   - что почитать;
   - подсказки;
   - критерии приёмки.
2. **Старт.** Автор пишет: «приступаю к Task X.Y».
3. **RED (Claude).** В ветке `wN/<тема>` Claude пишет все тесты задачи из Step 1, включая fake-реализации и хелперы, и коммитит их как `test(<pkg>): …`. Код задачи Claude не пишет.
4. **Заглушки (автор).** Автор создаёт типы и функции с точными сигнатурами из карточки, которые возвращают нулевые значения. После этого тесты компилируются и **падают на assertions**. Нужно убедиться, что каждый тест падает по ожидаемой причине.
5. **GREEN по одному тесту (автор).**
   - Тесты проходим в порядке списка: `go test -race -run '^TestИмя$' ./пакет/`, для строки табличного теста `-run '^TestBackoff/attempt_1$'`.
   - На каждый тест пишем минимальный код, после зелёного делаем рефакторинг и прогоняем `go test -race ./...`.
   - Наперёд код не пишем: случаи из следующих тестов реализуются только когда до них дошла очередь.
6. **Тесты автор не меняет.** Если тест кажется неверным или неудобным, автор пишет об этом, обсуждаем, правку делает Claude. Подгонять тест под код запрещено.
7. **Сдача.** Все тесты задачи зелёные, `make lint` чистый, `make test` и `make test-integration` зелёные. Автор коммитит `feat(<pkg>): …` (можно несколькими коммитами) и пишет: «Task X.Y готов к ревью».
8. **Ревью (Claude)** по диффу задачи, как строгий тимлид. Автор исправляет замечания. Если для исправления нужен новый тест, его пишет Claude.
9. **PR недели.** Все задачи недели в ревью приняты → PR `wN/<тема>` → `main`, зелёный CI, мерж.

**Задачи [Claude]** идут по классическому циклу «один тест за раз»:
- RED с заглушкой, которая возвращает нулевые значения (`panic("not implemented")` не годится, это не провал assertion);
- проверяем, что тест падает по правильной причине;
- минимальный GREEN, затем `go test -race ./...`, затем REFACTOR.

**Код без падающего теста не пишем.** Исключения:
- конфиги: Makefile, compose, Dockerfile, CI, `.golangci.yml`;
- SQL-миграции, их проверяет `TestPool_MigrationsApplied`;
- `cmd/taskq`, его проверяют ручные шаги «Проверка».

## Решения, которые уточняют спеку

1. **`Handler` и `PayloadValidator` переехали из `handlers` в `job`.** Если `Registry.Get` возвращает `handlers.Handler`, тип `*Registry` не удовлетворит интерфейс воркера `Get(string) (worker.Handler, bool)`, потому что в Go сигнатуры методов должны совпадать точно (ковариантности нет). Общий контракт в `job` решает это без зависимости `worker → handlers`.
2. **ID задачи и номер попытки передаются в обработчик через `context`** (`job.WithMeta` / `job.MetaFrom`). Без этого `webhook` не сможет выставить заголовки `X-Taskq-Job-Id` и `X-Taskq-Attempt`: в сигнатуре `Handle` есть только `ctx` и `payload`.
3. **Claim выполняется в `context.WithTimeout(context.WithoutCancel(rootCtx), 5s)`.** Если отменить запрос в момент, когда сервер его уже закоммитил, задачи останутся в `running` до истечения аренды.
4. **Линтер закреплён в отдельном `tools/go.mod`**, чтобы зависимости golangci-lint не засоряли основной `go.mod`.
5. **`GET /jobs` запрашивает у store `limit+1` строк**, чтобы точно знать, есть ли следующая страница.
6. **`POST /jobs` с кодом 201 возвращает заголовок `Location: /jobs/{id}`.**

## Review Focus

1. **Огромный номер попытки в `Backoff`** (64 и больше, например после многократного подбора задачи с истёкшей арендой) не должен переполнять сдвиг: ожидаем потолок `[5m, 10m)`. Тест в Task 1.2.
2. **`payload` не JSON-объект** (`null`, массив, строка, поле отсутствует) → 400 `payload: must be a JSON object`. JSONB `null` — валидное NOT NULL-значение, БД такое не отловит. Тест в Task 2.3.
3. **Один `idempotency_key` в 10 параллельных запросах** → ровно одна задача, ни одной ошибки 500. Тест в Task 1.3.
4. **Мусорные query-параметры в `GET /jobs`** (`status=foo`, `limit=0|201|abc`, `after_id=abc|-1`) → 400, а не пустой список или 500. Тест в Task 2.5.
5. **SIGTERM, пока Claim уже выполняется** → забранные задачи выполняются и завершаются, а не остаются «осиротевшими». Тест в Task 3.3.
